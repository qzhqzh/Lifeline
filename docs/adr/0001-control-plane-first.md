# ADR-0001：采用控制平面优先，而不是超级 Agent

- 状态：Accepted
- 日期：2026-08-01
- 决策者：Lifeline 项目

## 背景

Lifeline 需要长期管理多个项目，持续执行扫描、规划、排期、代码修改、测试、审查、发布和复盘。一个直观方案是构建一个拥有超长上下文、可以持续循环的“超级 Agent”，让它记住所有项目状态并自行决定下一步。

该方案存在以下结构性问题：

- 模型上下文不是可靠持久化存储；
- 对话压缩、模型升级和进程中断会丢失状态；
- 模型无法保证状态机、预算、权限和幂等性；
- 长循环难以审计、暂停、恢复和补偿；
- 项目进度容易退化为模型主观判断；
- 具体模型、Prompt 和工具会形成强耦合；
- 多项目资源冲突和排期无法仅靠 Agent 自律解决。

## 决策

Lifeline 采用“确定性控制平面 + 可替换智能执行器”的架构。

### 控制平面负责

- 项目事实；
- 工作包和依赖；
- 状态机；
- 版本化计划；
- 资源、预算与调度；
- 权限和审批；
- 持久工作流；
- 证据与审计；
- 中断恢复与补偿。

### 模型与执行器负责

- 扫描归纳；
- 规划建议；
- 代码实现；
- Bug 诊断；
- 独立审查；
- 优化建议；
- 研究和文档。

模型只提交 Proposal、Artifact 和 Evidence Candidate，不能直接提交正式项目事实。

## 关键约束

1. PostgreSQL 是项目事实来源；
2. Git 是代码与配置版本来源；
3. 持久工作流引擎保存长期流程状态；
4. 对象存储保存日志、报告、截图和补丁；
5. 向量检索只用于辅助上下文，不作为事实数据库；
6. 业务流程通过能力档调用模型，不硬编码具体模型名称；
7. 所有高风险动作经过确定性策略和人工审批；
8. 所有 `Verified` 状态必须具备可追溯证据。

## 备选方案

### 方案 A：单一超级 Agent

**优点**

- 初期原型快；
- 对话体验自然；
- 代码量少。

**拒绝原因**

- 难以恢复和审计；
- 状态不可验证；
- 容易无限循环和重复执行；
- 无法稳定控制预算和权限；
- 不适合多项目长期运行。

### 方案 B：完全依赖现有项目管理系统

**优点**

- 看板、Issue 和协作能力成熟；
- 可以快速开始。

**拒绝原因**

- 缺少模型路由、算力调度、运行回放和证据验收；
- 难以表达持久执行、资源预留和突破窗口；
- 无法成为多个执行器的统一控制平面。

现有项目系统可以作为早期界面或同步目标，但不能成为 Lifeline 的完整核心。

### 方案 C：完整事件溯源

**优点**

- 理论上可完整重建状态；
- 审计能力强。

**暂不采用原因**

- MVP 复杂度过高；
- 查询模型、迁移和调试成本大；
- 团队规模和当前业务复杂度不需要。

首期采用“事务状态表 + append-only 领域事件 + Outbox Pattern”，未来在确有需要时再演进。

## 结果

### 正面结果

- 模型、供应商和执行器可以替换；
- 长任务可以暂停、恢复和重试；
- 项目状态和排期可追溯；
- 权限、预算和资源规则可以严格执行；
- 可以建立真实的模型成功率和单位成本评测；
- 手机入口只需调用控制平面，无需直接操作执行器。

### 代价

- 初期工程量高于单一 Agent 原型；
- 需要维护领域模型、状态机和工作流；
- 必须为每种外部执行器实现适配器；
- 需要处理幂等性、补偿和审计。

这些代价被认为是构建长期可靠个人研发操作系统所必须承担的复杂度。

## 后续决策

后续需要单独形成 ADR：

- 事务表与审计事件的具体边界；
- Temporal 工作流粒度；
- Agent 事件协议；
- 执行沙箱安全模型；
- 模型策略与路由配置方式；
- GitHub App 身份与临时凭据方案；
- 单体模块化与服务拆分时机。
