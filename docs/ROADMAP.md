# Lifeline 路线图

> 本路线图按“端到端闭环优先”设计。每个阶段都必须形成可运行、可验证的增量，避免先建设大量基础设施却长期无法产生真实项目进展。

## 总体阶段

| 阶段 | 目标 | 关键交付 |
|---|---|---|
| M0 | 工程与领域骨架 | Monorepo、Schema、状态机、开发环境 |
| M1 | 只读项目指挥中心 | GitHub 接入、快照、健康度、证据进度 |
| M2 | 规划与情景排期 | 工作包、依赖图、计划版本、影响模拟 |
| M3 | 受控代码执行 | Worktree、执行器、测试、审查、PR |
| M4 | 模型路由与算力调度 | 能力档、预算、并发、突破窗口 |
| M5 | 评测与自适应 | Golden Tasks、Shadow Run、策略校准 |
| M6 | 多入口与扩展生态 | Telegram/移动端、MCP、远程 Worker |

---

## M0：工程与领域骨架

### 目标

建立可持续演进的工程基础，不接入真实自动化写代码。

### 范围

- pnpm + Turborepo Monorepo；
- React Web 应用；
- NestJS + Fastify API；
- PostgreSQL + Prisma；
- Temporal Server 与 Worker；
- 本地 Docker Compose；
- 统一配置、日志、错误结构；
- 项目、工作包、运行、证据、审批的最小 Schema；
- 业务、执行、排期、审批四类状态分离；
- OpenTelemetry 基础埋点；
- CI：lint、typecheck、test、build。

### 验收标准

- `docker compose up` 可启动数据库、Temporal、API 和 Web；
- 能创建项目、里程碑和工作包；
- 状态机拒绝非法跃迁；
- Temporal 示例工作流可暂停、恢复和重试；
- CI 在干净环境完整通过；
- 所有领域状态变化生成审计事件。

### 退出条件

领域模型和状态机稳定到足以支撑 M1，不再以临时 JSON 或前端 Mock 作为事实来源。

## M1：只读项目指挥中心

### 目标

让 Lifeline 能客观回答“所有项目现在怎么样”。

### 范围

- GitHub App 或 Token 接入；
- 仓库、默认分支、提交、Issue、PR、Check Run 同步；
- Webhook 与增量拉取结合；
- 项目快照；
- 快照差异；
- 项目健康度；
- 证据驱动进度；
- Portfolio Command Center；
- Project Cockpit；
- 最近有效进展与长期无变化检测；
- 扫描运行回放。

### 扫描顺序

1. GitHub 确定性数据；
2. 仓库结构与配置解析；
3. 快速模型生成摘要；
4. 强模型仅分析异常与高价值区域；
5. 规则校验后形成项目快照。

### 验收标准

- 可以接入至少 3 个真实仓库；
- 首次扫描生成可追溯快照；
- Webhook 后 5 分钟内反映主要状态变化；
- 快照可以比较“新增、完成、阻塞、退化”；
- 项目进度由证据计算而不是手工百分比；
- 扫描失败可重试且不会产生重复数据。

### 明确不做

- 不自动修改代码；
- 不自动创建正式排期；
- 不尝试完整理解所有源码。

---

## M2：规划与情景排期

### 目标

让 Lifeline 能回答“下一步应该做什么，调整后会影响什么”。

### 范围

- Epic、Feature、Task、Bug、Research、Ops 工作包；
- 工作包执行契约；
- 依赖图；
- Planner；
- Independent Critic；
- 工期区间和资源估计；
- 正式、暂定和情景三类排期；
- 不可变 `schedule_version`；
- 拖动排期后的影响模拟；
- 人工批准与驳回；
- 计划变更审计。

### 初始排期逻辑

M2 只实现可解释规则：

- 前置依赖；
- 截止日期；
- 战略优先级；
- 工作包估计区间；
- 模型/API 预算；
- 人工审查时间；
- 项目切换惩罚；
- 缓冲时间。

暂不引入复杂求解器。

### 验收标准

- Planner 输出必须通过 Schema 校验；
- 所有正式计划变更存在版本和 Diff；
- 用户可比较至少两个情景排期；
- 系统能说明任务延期对其他项目的影响；
- 没有验收标准的工作包无法进入 `Ready`；
- 用户可以在评审后一次性批准一组计划变更。

---

## M3：受控代码执行

### 目标

完成 Lifeline 的首条真实端到端自动开发闭环。

### 范围

- `AgentExecutor` 统一接口；
- 首批 Codex Adapter 与 Claude Adapter；
- Git branch/worktree 管理；
- rootless Docker 隔离；
- 工作包上下文打包；
- 执行日志与事件流；
- 测试命令；
- Repair Loop；
- Independent Reviewer；
- PR 创建；
- CI 状态回传；
- 人工审批；
- 合并后快照更新。

### 执行规则

- 一个工作包对应一个独立分支和 Run；
- 默认禁止直接推送主分支；
- 实现模型与审查模型必须隔离；
- 失败两次后升级能力档或转人工；
- 高风险文件、迁移和生产配置需要额外审批；
- 工作包输入在 Run 开始时冻结，变化后需重新评估。

### 验收标准

- 一个真实功能可以从 `Ready` 自动推进到 PR；
- 每次执行可完整回放；
- 所有改动都有测试或明确的人工验收；
- Worker 重启后 Run 能恢复或安全终止；
- 相同 Webhook 或 Activity 重放不会重复创建 PR；
- 失败 Run 不污染主分支和其他 Run。

## M4：模型路由与算力调度

### 目标

根据任务、风险、预算和资源自动选择执行路径，并支持集中突破。

### 范围

- 能力档 Registry；
- Provider/Model 配置；
- 成本、上下文、工具和隐私限制；
- 升级、降级和故障切换；
- 资源池与资源预留；
- 优先级队列；
- 并发限制；
- API 日预算和单任务预算；
- 可抢占后台任务；
- Focus Window；
- Compute Console。

### 资源池

- 本地 CPU/GPU；
- 远程 Worker；
- 各代码 Agent 并发槽位；
- API 预算；
- CI Runner；
- 部署槽位；
- 人工审查时间。

### 验收标准

- 路由决策有可解释原因；
- 超预算任务不会启动；
- 高优先级任务可抢占允许抢占的后台任务；
- 突破窗口可以限制项目、预算、并发和结束时间；
- 调度器重启不会丢失队列和资源占用；
- 用户可以查看每个项目的实时资源消耗。

---

## M5：评测与自适应

### 目标

让 Lifeline 通过真实运行数据改进模型和调度策略。

### 范围

- Golden Task Set；
- 任务类型化评测；
- 成功率、单位成功成本、人工修正率；
- Trace 评分；
- Shadow Run；
- 模型与 Prompt 版本；
- 路由策略实验；
- 工期估计校准；
- 自动识别长期阻塞和低收益任务。

### 验收标准

- 每个核心能力档至少有 10 个代表性样本；
- 新模型上线前必须完成 Shadow Run；
- 可以比较同类任务在不同模型上的成功率和成本；
- 估算偏差可以按项目、任务类型和模型统计；
- 策略变更可回滚；
- 自动优化不能绕过安全与审批规则。

---

## M6：多入口与扩展生态

### 目标

在核心控制平面稳定后，让用户在离开电脑时仍可安全管理项目。

### 范围

- Telegram Bot；
- 移动 Web/PWA；
- 语音转结构化命令；
- 审批摘要；
- MCP 工具接入；
- 外部 Worker 注册；
- 专业 Agent 服务；
- 必要时评估 A2A；
- 通知与每日项目简报。

### 手机端允许的首批动作

- 查询状态；
- 新建想法；
- 发起扫描；
- 批准计划提案；
- 暂停或取消 Run；
- 启动低风险突破窗口。

### 验收标准

- 每个移动命令都映射到明确 API 与权限；
- 高风险动作必须跳转到完整审批；
- 重复消息不会重复创建任务；
- 通知包含项目、影响、成本、证据和可撤销动作。

## 建议发布节奏

### Alpha

覆盖 M0 + M1：能够统一查看项目真实状态。

### Private Beta

覆盖 M2 + M3：能够从计划推进到受控 PR。

### Beta

覆盖 M4：能够自动选择模型和进行集中突破。

### 1.0

覆盖 M5 的核心评测能力，并经过多个真实项目持续运行验证。

## 每阶段的硬性原则

1. 必须有至少一个真实项目作为验证对象；
2. 必须能从 UI 看到输入、状态、证据和结果；
3. 必须测试中断、重试和幂等性；
4. 不以“模型输出了 Markdown”作为功能完成；
5. 不提前建设下一阶段的大型基础设施；
6. 所有新自动化都必须有停止、恢复和人工接管路径。
